_Last updated 2026-07-29. Groups core (5a of the groups suite) is on branch `phase-5a-groups-core` with a PR open; next after merge: groups PR 2, the people layer._

**Architecture (settled, do not relitigate):** React Native/Expo (SDK 54), Supabase-only backend (RLS + SECURITY DEFINER RPCs; Edge Functions later for push/AI; no Express — deleted in Phase 0 after explicit discussion). User-facing word is **"Groups"** (never "Circles"); profile is the **12b/14a menu-style sheet** (read-only, Edit button, Send-feedback row). The user is sensitive to unflagged structural changes AND to deviations from the design doc — if implementing less/differently than the design shows, say so explicitly first.

**Product decisions made in Phase 4 (apply everywhere):**
- **Host counts from creation**: posting a fixed plan auto-inserts the creator's yes-RSVP; posting a flexible plan auto-inserts their availability on every proposed day. An 11-person plan opens at "10 more".
- **Cap ≥ min** (diverges from the design script's cap > min, user-requested): cap-up from "No limit" lands on min itself; a climbing min drags the cap along to match; exact headcount (min == cap) is valid.
- **Dates render en-GB** ("Fri 31 Jul", "Friday 31 July") app-wide; the design mocks are en-US.
- **HARD RULE — never string-parse dates on Hermes.** `new Date('YYYY-MM-DD')` is UTC midnight (stored flexible options a day early on negative UTC offsets) and `new Date('…T20:30:00')` disagrees with the native picker's offset (wheel showed 19:30 for a 20:30 pill). Always build via `new Date(y, m-1, d, h, min)`. Both bugs shipped and were fixed in PR #6 — don't reintroduce.
- Known data caveat: flexible plans seeded **before** PR #6 still carry UTC-midnight option dates and may display a day early on negative-offset timezones; new plans are correct.

**Product decisions made in Phase 5 (groups):**
- **Friends are in scope** (user decision 2026-07-29): the design file is ordered newest-iteration-first — 18a IS the Groups tab, and 17b (Find people) / 17c (new circle from your people) are the two screens it leads to. Friendship is by consent (Add → Requested → Accept/Ignore, handles displayed), which the user thinks of as Telegram-style contacts. `profiles.handle` was pulled forward from the profile slice because friend requests display it.
- **Invites are both link- and person-based**: the invite code survives as the payload of a shareable `planazo://join/<code>` link (only works with the app installed — no web domain yet); person invites go through `group_invites` + RPCs and will surface in the 18b sheet (PR 2).
- **Reconciliations applied in PR 1** (flagged, not silent): list rows use 18a's compact single-card structure but keep 6a's ember "N plans waiting on you" meta (6a's caption argues for it explicitly); rows drop desc/admin-chip per 18a. Group detail is a pushed screen without the tab bar (consistent with plan detail), so the 6b empty state gets an explicit "Start a plan" CTA into the 5a preseed instead of pointing at the tab-bar +. Detail/manage "Invite" is a native share sheet of the join link until 6d lands in PR 2. 6e's "Rename or recolour" target isn't designed — implemented as a minimal modal in the create screen's visual language. The 6d prose's "turn the link off in Manage" toggle is skipped (the 6e behavior script has only the two toggles).
- **leave_group semantics**: last admin leaving promotes the longest-standing member; the last member leaving deletes the group (an orphaned group would be unreachable).
