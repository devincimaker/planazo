## Last phase: integration test suite vs local Supabase in CI

**Why it exists (motivating bugs):** mocked jest tests structurally cannot see RLS/trigger behavior. Real bugs only caught on-device: pending invitees were RLS-blocked from reading the invited group's name (fixed in `20260729000002`), plus two date bugs. This suite is the regression net for everything the DB does.

**What to cover (in rough priority):**
1. **RLS**: invitee can read the invited group's name pre-acceptance; non-members can't read a group's plans/members; `anyone_can_post=false` blocks member plan INSERT but not admin; notifications are select/update-own only.
2. **RPCs**: `lock_plan` (seeds yes-RSVPs from availability), `cancel_plan(p_plan_id, p_reason)` (stamps cancelled_at/by/reason, notifies yes-RSVPs + available voters minus canceller, host/admin-only), `restore_plan` (cancelled-only, date-ahead guard, locked-vs-open restore, `plan_reopened` notices), `leave_group` (cleans rsvps/availability, promotes longest-standing member when last admin leaves, deletes empty group), `send_friend_request`/`respond_friend_request` (crossing requests auto-accept), `invite_to_group`/`respond_group_invite`, `set_group_notify`.
3. **Triggers**: `trg_notify_plan_created` (fans out to members with `notify_new_plans`, excludes creator, fixed-vs-flexible copy); `handle_new_user` (profile + permanent handle); `trg_push_notification` must NEVER break an insert — locally Vault has no `send_push_secret`, so the webhook silently skips: assert notification inserts still succeed (that silence is itself the tested behavior; the HTTP hop is live-verified, don't try to test it in CI).

CI: extend `.github/workflows/ci.yml` (typecheck + jest + vitest via turbo already) with a job using `supabase/setup-cli` + `supabase start` (or `db start` is NOT enough — auth is needed). Docker is available on ubuntu runners.
